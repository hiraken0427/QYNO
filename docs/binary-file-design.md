# バイナリファイル操作（新段階9、0.27.1）

状態: 0.27.1で実装済み。第11節の後続機能は未実装。
0.27.1では通常ファイルのバイト列の読み書きだけを追加する。
既存のfile型、名前空間、共有ハンドル、明示close、通常の配列を活用する。

## 1. 対象とAPI

`io.file` に追加する。標準モジュールなのでimportは不要。
修飾名・選択using・一括using・モジュール別名は0.27.0の規則に従う。

| API | 戻り値 | 動作 |
| --- | --- | --- |
| `open(path, "rb")` | file | 既存の通常ファイルをバイナリ読み取り用で開く |
| `open(path, "wb")` | file | バイナリ書き込み用。既存内容を長さ0にするか新規作成 |
| `open(path, "ab")` | file | バイナリ追記用。なければ新規作成 |
| `read_bytes(file source, int_64 count)` | unsigned int_8の1次元配列 | 現在位置から最大countバイト読む |
| `write_bytes(file destination, unsigned int_8 data[])` | int_64 | 全要素を1要素1バイトで書き、書いたバイト数を返す |

表は組み込みAPIの説明記法であり、新しい配列型の構文ではない。
戻り値の配列は通常のQYNOの `unsigned int_8 name[]` で受け取る。
新しいbyte型・bytes型・ポインタ型は追加しない。
countは必須で、既定値や「省略すればEOFまで」の動作は設けない。
新APIはconstの初期値には使えない。実行時の入出力として扱う。

## 2. モードと権限

| モード | read / readline | write | read_bytes | write_bytes |
| --- | --- | --- | --- | --- |
| r | 可 | 不可 | 不可 | 不可 |
| w / a | 不可 | 可 | 不可 | 不可 |
| rb | 不可 | 不可 | 可 | 不可 |
| wb / ab | 不可 | 不可 | 不可 | 可 |

openの省略モードは従来どおり `"r"`。
`"r"`・`"w"`・`"a"` のUTF-8・改行・BOMの動作を変えない。
文字列は完全一致。`"br"`・`"r+b"`・`"rb+"`・大文字・空白付きなどは受け付けない。
定数の不正なモードはコンパイルエラー、動的な不正モードは実行時エラー70。

file型そのものはテキスト用・バイナリ用に分けず、ハンドルの状態としてモードを保持する。
開いたハンドルに対して別種のAPIを呼んだ場合は、既存の権限違反と同様に実行時エラー70。
その呼び出しでファイル内容や論理位置を変更する前に拒否する。
全ての別名・引数渡しでモードの制約を共有し、後からモードを切り替える操作は追加しない。

この区別はQYNOのAPI契約であり、Linuxのファイル自体にテキスト属性を付ける意味ではない。
同じパスを別の適切なモードで開き直すことは可能。元のハンドルのclose責任は残る。
close・is_open・ハンドル比較は全モードで同じ。

## 3. バイトの意味

unsigned int_8の各要素が0〜255のバイト1個を表す。
0x00・0xff・不正UTF-8・改行・BOMを含む任意の列を、そのまま保持する。
符号化の解釈、UTF-8検証、改行変換、BOMの追加・除去、終端NULの追加は行わない。
パスはバイナリモードでも従来どおりUTF-8で検証し、WindowsではUTF-16へ変換する。

配列の内部メモリをそのまま読み書きしてはいけない。
現在の配列要素はABI上8バイトのスロットだが、ファイル上では1要素が1バイトになる。
要素数・容量・shape・参照・GC管理情報・パディングは保存しない。
バイト列にCPUのエンディアンは関係しない。複数バイト整数の直列化は後続の別APIとして設計する。

```text
unsigned int_8 data[] = [0x00, 0x7f, 0x80, 0xff]
// write_bytesは 00 7f 80 ff の4バイトを書き込む。
// 32バイトの配列スロット領域をそのまま書く処理ではない。
```

## 4. read_bytesの結果・EOF・位置

countには通常のint_64引数の型変換規則を適用する。
intなどの適合する整数は受け付けるが、小数・bool・範囲外整数を暗黙に切り詰めない。
int_128やunsigned int_64等から必要な場合は、範囲検査付きの `int_64(count)` を明示する。

| 条件 | 結果 |
| --- | --- |
| countが負 | 定数ならコンパイルエラー、動的ならエラー70 |
| count=0 | 独立した空配列。ハンドル検査は行うがOSのread・位置変更は行わない |
| count>0でcountバイト以上読める | count要素の配列 |
| count>0で途中でEOF | 読めた分だけの配列。0埋めしない |
| count>0で最初からEOF | 空配列 |
| OSの読み取り失敗 | エラー74。EOFや短い成功結果に置き換えない |

正のcountでは、OSが少量だけ返してもそれだけで終了せず、countに達するかEOFまで読み続ける。
LinuxのEINTRは再試行する。戻り値がcountより短い成功結果は、その呼び出しでEOFに達したことを表す。
対象はブロッキングの通常ファイルであり、パイプ・ソケット・端末は今回の対象外。

返す配列の長さが実際に読んだバイト数。戻り値の各配列は独立し、
次の読み取り、ファイルのclose、返した配列の変更は、以前の配列の値に影響しない。
読み取りに成功したバイト数だけ共有ハンドルの論理位置を進める。
先読みバッファの未消費分を先に使用し、OS側の位置と論理位置を混同しない。

EOFは永続的にキャッシュしない。後から追記された場合は、EOF後の呼び出しでも再び読み取りを試みる。
他プロセスがファイルを変更している間の内容について、呼び出し全体のスナップショットは保証しない。
途中まで読んだ後のOS失敗やメモリ不足では配列を返さず停止する。ファイル位置の巻き戻しは保証しない。

### 確保量と上限

countは読み取り件数の上限であり、最初にcount要素を全て確保する要求ではない。
実際に読めたデータに応じて段階的に確保し、空ファイルへの巨大なcount指定だけで巨大確保を行わない。
count=INT64_MAXでも、実際に1バイトしか読めなければ1要素の結果を返せる。
現在の配列・アロケーターで表現できる範囲を超える場合や確保失敗は、診断付きのエラー70。
要素数の増加、容量拡大、要素数×8、管理領域を加えた確保サイズを全て範囲検査する。
OSへ渡す1回の件数は各OSの上限以内に分割する。

### 受け取り先の配列

EOFをlengthで判断する用途では、必ず上限を省略した配列を使う。

```text
unsigned int_8 block[] = io.file.read_bytes(source, 65536)
```

`unsigned int_8 block[65536] = ...` と書くと、通常の配列初期化の不足要素補完が適用され、
短い読み取りでもblock.lengthは宣言された長さになる。バイナリAPI専用の初期化例外は追加しない。
件数を調べるための新しいeof関数や別のbytes_read関数は初版では追加しない。

## 5. write_bytesの型・完了・追記

引数はunsigned int_8の1次元配列だけを受け付ける。
const配列、readonly参照から見える配列、1次元の子配列、同じ型の配列を返す式も利用できる。
int[]・int_8[]・unsigned int_16[]・str・char[]・2次元配列を暗黙変換しない。
例えば0〜255だけを含むint[]でも拒否し、バイト列であることを型で明示する。
直接の配列リテラルは期待型unsigned int_8[]で検査し、`write_bytes(f, [0x00, 0xff])` や空の `[]` を許可する。
要素は通常の型変換規則でunsigned int_8に適合する必要があり、負の定数や256以上の定数は拒否する。

dataは組み込み処理が読み取り専用で観測する。呼び出し側にrefは付けない。
`write_bytes(destination, ref data)` は引数の誤用としてコンパイルエラーとする。
通常関数の配列値渡しのような深いコピーや、全体を詰め直した巨大な一時領域は作らない。
有限サイズの作業バッファへバイトを詰め、順番に書き込む。入力配列を変更しない。

全バイトを書き終えた場合だけ成功し、戻り値はdata.lengthと等しいint_64のバイト数。
OSの短いwriteは残りを再試行し、EINTRも再試行する。
残りがあるのに書き込みが0バイトで進まない場合はエラー74とし、無限に再試行しない。
空配列でもハンドルとモードを検査し、正常ならOSのwriteを呼ばず0を返す。

失敗した場合、すでに書いた部分は取り消さない。呼び出し全体の原子性やロールバックは保証しない。
正常終了はOSが全バイトを受け付けたことを表す。記憶装置への永続化保証やfsyncは追加しない。
closeの失敗は既存どおり通知する。

abは各OSのappend機能を使い、各OS書き込みがその時点の末尾に追加されるようにする。
open時に一度だけ末尾へ移動して通常writeする実装にはしない。
作業バッファの分割等によって、他の書き込みとの間にデータが挟まる場合がある。
複数プロセスに対するwrite_bytes呼び出し全体の不可分性は保証しない。

## 6. 評価順・借用・close・readonly

引数式は左から順に1回だけ評価し、その後でハンドル・モード・件数を検査する。
引数評価の副作用は省略しない。後の引数評価で共有ハンドルが閉じられた場合も、検査時点の状態で拒否する。
不正な件数やモードによるAPI本体の失敗では、読み書きや論理位置の変更を開始しない。

fileの値渡し・配列内のfile・別名は既存どおり同じハンドルを共有する。
read_bytes・write_bytesは現在位置や外部の内容を変えるためreadonlyのfileでは使用できない。
write_bytesのdataだけはreadonlyを許可する。
新APIはハンドルの所有権を受け取らず、自動でcloseしない。
借用したハンドルに新しいclose責任を作らず、openが作った既存の責任をそのまま追跡する。
正常終了の全経路で明示closeが確認できない場合は引き続きコンパイルエラー。
到達可能なbreak / returnを持つwhile(true)は、その出口からcloseを追跡する。
出口のない無限ループへの未closeハンドルの持ち込みや、反復中の資源の取り残し・別名の消失は従来どおり拒否する。

## 7. libとの関係

取得した `unsigned int_8 data[]` について:

- `data.length` と `lib.length(data)` は現在のバイト数。
- `lib.size(data)` は現在の要素数×8のビット数（int_64で表現できる範囲内）。
- `lib.size(data[i])` は8。
- lib.sizeは実際に確保した配列スロットのメモリ量を表さない。
- lib.size(file)は引き続き対象外。ファイル全体のサイズ取得は後続のio.file.sizeで扱う。

io.print(data)は従来の配列表示であり、ファイルの生バイトをコンソールへ送る処理にはしない。
文字列への符号化・復号、数値へのエンディアン付き変換も今回追加しない。

## 8. 使用例

### 分割してバイナリファイルをコピーする

```text
using io.file as fs

int main();
	file source = fs.open("image.bin", "rb")
	file destination = fs.open("copy.bin", "wb")
	while(true);
		unsigned int_8 block[] = fs.read_bytes(source, 65536)
		if(block.length == 0);
			break
		fs.write_bytes(destination, block)
	fs.close(destination)
	fs.close(source)
	return 0
```

コピー元とコピー先は別のファイルを指定する。wbはopen時に切り詰めるため、
同じ実体のパスを指定したコピーを安全にする機能はこの例には含まれない。
同一ファイルの検出や上書き制御は、将来のio.file.copyの契約として設計する。

### バイト列を書き出し、追記する

```text
using io.file as fs

int main();
	unsigned int_8 header[] = [0x51, 0x59, 0x4e, 0x4f, 0x00, 0xff]
	file destination = fs.open("sample.bin", "wb")
	int_64 written = fs.write_bytes(destination, header)
	fs.close(destination)
	io.print("{written} bytes / {lib.size(header)} bits") // 6 bytes / 48 bits

	file tail = fs.open("sample.bin", "ab")
	unsigned int_8 ending[] = [0x0d, 0x0a]
	fs.write_bytes(tail, ending)
	fs.close(tail)
	return 0
```

## 9. エラー分類

| 分類 | 例 | 結果 |
| --- | --- | --- |
| 型・構文 | 件数の型不一致、dataの型/次元不一致、不正引数数、refの誤用、readonly file、未close | コンパイルエラー1 |
| 定数で分かる不正引数 | 不正なモード、負のcount | コンパイルエラー1 |
| 正常な終端 | 正のcountでEOF | 実際に読めた分。最初からEOFなら空配列 |
| パスの符号化 | 不正UTF-8のパス | 実行時エラー65 |
| APIの使い方 | 未オープン・閉じたfile、モード不一致、動的な負のcount、NUL入りパス、不正な動的モード | 実行時エラー70 |
| 記憶領域 | 件数・容量・確保サイズの範囲超過、メモリ不足 | 実行時エラー70 |
| OSのI/O | open/read/write/close失敗、通常ファイル以外 | 実行時エラー74 |

バイナリの内容そのものを理由にUTF-8エラー65にはしない。
既存の呼び出し元ファイル・行・列・操作名・パス・OSエラー情報による診断を再利用する。
EOF、空データ、OS失敗を同じ結果にまとめない。

## 10. 実装順と検証

1. builtin登録、モードの定数検査、ハンドルのモード表現と権限検査を拡張する。
   OSへのopen権限はr/w/aに対応させ、binary属性を別に保持する。
   既存の数値大小比較によるモード判定へフラグを単純追加して誤許可しない。
2. read_bytesの型検査、1次元unsigned int_8配列の戻り値、バッファと位置の処理を実装する。
   count要素の先行一括確保をせず、範囲検査付きで実読みに応じて増やす。
3. write_bytesの読み取り専用の配列観測、有限バッファへの詰め替え、全量書き込みを実装する。
4. readonly・明示close解析・別名・関数・model経由でも新APIを既存規則で扱う。
5. VS Codeの標準カタログ・補完・引数ヒント・診断とサンプル・文書を更新する。
6. 実装時にCLIと期待値、拡張の表示名・版を0.27.1へ同期する。
   個別検証後に全体テストを1回成功させ、VSIXを作成し、devへ1回pushしてZIPを作成する。
   ZIPの展開後の再テストはせず、次の実装指示を待つ。

検証対象:

- 全256値、NUL、CR/LF/CRLF、BOM、不正UTF-8を含む列の完全な往復。
- 空ファイル、count=0/1/大きい値、空ファイルへのINT64_MAX指定、countより短いファイル。
- 読み取りバッファ境界の直前・一致・直後、大きな分割読み、異なるcountでの連続読み。
- 共有ハンドルの別名間での位置共有、返した配列の独立性、EOF後の追記と再読み取り。
- 空配列・const/readonly・子配列・戻り値式・配列リテラルの書き込み、誤った型・次元・範囲外要素・負の件数の拒否。
- 全モードの権限表、既存テキストAPIの回帰、動的モード・閉じた/未オープンfileへの空操作の拒否。
- 引数の副作用が1回かつ左から順であること、不正引数でAPI本体の位置変更を行わないこと。
- 途中のOS短読み・短書き・EINTR・0バイト書き込み・失敗を注入して再試行と診断を確認。
- wbの切り詰め、abの末尾追記、他ハンドルの追記、配列に内部スロットの余分なバイトを保存しないこと。
- 正常終了の全経路のclose責任、readonly fileの拒否、const/readonly dataの受け入れ。
- サイズ計算と確保失敗の検査は巨大な実メモリ確保を行わず、境界値の検査や失敗注入で確認。
- Linux / Windows実行、アセンブリ出力、VS Codeのusing・別名・型不一致・未close診断。

## 11. 次段階へ分けるもの

回復可能なI/Oエラー、seek / tell / ファイルサイズ、r+等の更新モード、
read_exact・既存配列へのread_into、パス指定の一括読み書き、ファイルのcopy / move / remove、
符号化変換、整数のエンディアン付き読み書き、構造体の直列化、flush / sync、非同期I/Oは対象外。
追加する場合も、今回の2関数のEOF・型・closeの契約は維持する。
